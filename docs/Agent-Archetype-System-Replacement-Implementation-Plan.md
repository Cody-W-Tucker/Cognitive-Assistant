# Agent Archetype System Replacement Implementation Plan

- Status: implementation-ready plan. This document changes no production code.
- Source: "Who Does What? Archetypes of Roles Assigned to LLMs During Human-AI Decision-Making" (arXiv:2602.11924v1). The concrete policy below is a project decision, not a claim about the paper.
- Objective: replace the three legacy archetypes with the 17-role catalog, add strict plan validation and domain policy, and rename `SOUL_ARCHETYPE.md` to `INTERACTION_POSTURE.md`.
- Non-goals: no compatibility layer, no dual-read of legacy artifacts, and no external side effects or external action authorization in v1.
- Encoding: every named source, generated artifact, prompt, JSON file, and test in this plan is strict ASCII.

---

## 1. Authority, scope, and lifecycle

`workspaces/alignment/artifacts/agent_plan.json` is authoritative only for the generated agent bundle:

- `workspaces/alignment/artifacts/persona_map.md`
- `workspaces/alignment/artifacts/agents/*.md`
- generated graph and governance metadata embedded in the final plan

It is not authoritative for `INTERACTION_POSTURE.md`. `INTERACTION_POSTURE.md` is an upstream generated input owned by `build-translation-layer`; it is not a projection of an agent plan and must never be regenerated by `build-agents`, validation, projection repair, or crash reconciliation.

The final plan persists the exact posture snapshot used by soul generation:

```json
"interaction_posture": {
  "path": "workspaces/alignment/artifacts/INTERACTION_POSTURE.md",
  "sha256": "<64 lowercase hex characters>",
  "markdown": "<exact ASCII Markdown bytes decoded as text>"
}
```

At build time, `sha256(UTF-8(markdown))` must equal `interaction_posture.sha256`, and the current file at `path` must have exactly those bytes and that hash before agent soul generation begins. Soul generation consumes the persisted snapshot, not a later file read. A stale, absent, non-ASCII, or mismatched posture input rejects the build.

## 2. Global strictness and scalar rules

All JSON objects in this plan are closed objects: every listed key is required unless marked nullable, and unknown keys reject. All arrays preserve stated order and reject duplicate members unless a type says otherwise. All strings are non-empty ASCII strings after trimming, except Markdown fields may contain ASCII newlines and `rationale` may be empty only where explicitly stated. JSON is UTF-8 on disk but its bytes must be ASCII.

| Scalar | Exact rule |
|---|---|
| `Id` | `^[a-z0-9]+(?:-[a-z0-9]+)*$` |
| `RoleSlug` | `Id`, and resolves to one of the 17 catalog slugs |
| `Path` | relative, non-empty, ASCII path; no leading `/`, `..`, or NUL |
| `Sha256` | `^[0-9a-f]{64}$` |
| `Markdown` | non-empty ASCII text; `\n` is allowed; no CR bytes |
| `Text` | non-empty trimmed ASCII string |
| `NonnegativeInt` | JSON integer `>= 0` |
| `DecisionControl` | `human`, `shared`, or `agent`; rank is human `0`, shared `1`, agent `2` |
| `Scope` | `internal` or `external` |
| `Boolean` | JSON boolean only |
| `GeneratedAt` | Canonical UTC timestamp matching `^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$`; parser must reject impossible calendar dates and times, offsets, and fractional seconds. |

No validator silently sorts, fills defaults, removes unknown keys, converts strings to enums, or invents nodes, actions, sources, gates, evidence, or policy. Parsers return either the exact typed value or a validation error with a JSON path.

For every cross-registry label comparison in this document, `normalized_label` is `lowercase(trim(label))`. Labels are already `Text`, so trimming does not change a valid label. No other Unicode, punctuation, or whitespace normalization is applied.

## 3. Catalog contract and exact role ledger

The canonical slugs are exactly `role-taker`, `model`, `communicator`, `explainer`, `knowledge-checker`, `decision-scaffolder`, `implicit-reasoner`, `second-opinion`, `alternative-perspectives`, `counterargument`, `user-aligner`, `consensus-generator`, `minority-opinion`, `formalizer`, `criteria-applicator`, `judge`, and `data-processor`.

`explainer` has variants `internal-model` and `external-model`; `knowledge-checker` has variants `internal-knowledge` and `external-knowledge`. Parent links are only `explainer: communicator`, `implicit-reasoner: decision-scaffolder`, `counterargument: alternative-perspectives`, and `minority-opinion: consensus-generator`. Parent links do not inherit permissions.

The normative `variants` records are exactly `[{"id":"internal-model","label":"Explainer of Own Model","provenance_mode":"internal-model"},{"id":"external-model","label":"Explainer of External Model","provenance_mode":"external-model"}]` for `explainer`, exactly `[{"id":"internal-knowledge","label":"Internal Knowledge Checker","provenance_mode":"internal-knowledge"},{"id":"external-knowledge","label":"External Knowledge Checker","provenance_mode":"external-knowledge"}]` for `knowledge-checker`, and exactly `[]` for every other role. These labels and provenance modes are literal records, not derived from an ID, slug, or display rule.

Every `profiles/alignment/archetypes/<slug>.json` is a closed object with this exact field set:

| Field | Type |
|---|---|
| `schema_version`, `slug`, `name`, `paper_label`, `paper_claim`, `implementation_note` | `Text`; schema version is `1.0-proposed` |
| `parent` | `RoleSlug` or `null` |
| `variants` | unique ordered `[VariantRecord]`, where `VariantRecord` is exactly `{id: Id, label: Text, provenance_mode: internal-model|external-model|internal-knowledge|external-knowledge}` |
| `role_inputs`, `role_outputs`, `prohibitions`, `quality_criteria`, `canonical_skills` | unique ordered `[Text]` |
| `decision_control` | `{allowed: [DecisionControl], default: DecisionControl}` |
| `knowledge` | `{allowed_modes: [internal|external|either], default_mode: internal|external|either, provenance_required: Boolean, citations_required_for_external: Boolean}` |
| `verification_diversity` | `{orientation: none|check|independent|adversarial|plural|consensus|formal|criteria|data, obligations: [Text]}` |
| `cognitive` | `{supported_modes: [direct|model|scaffold|implicit|counterfactual|formal|criteria|compute], default_mode: same enum, forcing_triggers: [TriggerId]}` |
| `social` | `{default_position: peer|service|advocate, role_override: peer|service|advocate|null}` |

| `composition` | `{primary_compatible_secondary: [RoleSlug], prerequisite_groups: [[Prerequisite]], conflicts: [RoleSlug], max_secondary: 3}` |
| `safeguards` | `{failure_modes: [Text], mitigations: [Text]}` |

`ActionSpec` is exactly `{id: Id, description: Text, min_decision_control: DecisionControl, scope: Scope}`. Action IDs are unique within a role and may not occur in that role's prohibited IDs. Every catalog action has `scope: "internal"`; a catalog containing an external action rejects. `max_secondary` is exactly `3`. `allowed`, `allowed_modes`, and all `default` values must be internally consistent. The role's `variants` field must equal its normative literal array above, including order, IDs, labels, and provenance modes. Only `role-taker` and `user-aligner` have a non-null social override. Only the two stated variant roles have non-empty variants.

### 3.1 Typed prerequisites and compact-cell serialization

`Prerequisite` is one of these closed discriminated records:

```json
{"kind":"role_present","role":"criteria-applicator"}
{"kind":"input_present","input":"criteria"}
{"kind":"criteria_present","criteria_key":"decision-criteria"}
{"kind":"external_model_output_present","role":"explainer"}
{"kind":"group_input_count","minimum":2}
{"kind":"registered_decision_present","decision_key":"operator-decision"}
{"kind":"profile_context_present","profile":"existential"}
```

The exact keys per kind above are mandatory; every other key rejects. `role_present` checks the candidate portfolio, `input_present` checks a declared role input or a resolving typed visible input, `criteria_present` and `registered_decision_present` check `context_registry` keys, `external_model_output_present` checks a reachable declared output of the specified role with external provenance, `group_input_count` counts distinct resolving source identities, and `profile_context_present` checks the normalized profile registry. A row with no prerequisites uses `[]`.

`prerequisite_groups` has inner-AND, outer-OR semantics: each inner list is an all-of group; the role is composable when at least one inner group passes. `[]` means no prerequisite. This removes prose alternatives such as "formalizer or explicit criteria".

In the ledger below, every compact cell is an exact JSON literal, not semicolon notation. `I/O/P` serializes respectively to `role_inputs`, `role_outputs`, and `prohibitions`. `A` serializes to `authority`; `Comp` serializes to `composition`; `Q` serializes to `quality_criteria`; `Skills` serializes to `canonical_skills`. Fields not variable in the ledger use the deterministic common policy in 3.2.

## 4. Composition, settings, and authorization

A generated agent has exactly one primary role and zero through three unique secondary roles. The primary role's `primary_compatible_secondary` is directional and complete. A conflict is symmetric at validation time: if either selected role lists the other, reject. Each active role's prerequisite groups must pass. All role inputs must be supplied by a resolving visible input, an upstream declared output, or a context entry. All required role outputs must be declared on that agent node. No secondary role may exceed the primary role's maximum.

Resolved settings have exactly these seven dimensions:

```json
{
  "decision_control":"human",
  "knowledge":{"mode":"internal","provenance_required":false,"citations_required_for_external":false},
  "verification_diversity":{"orientation":"none","obligations":[]},
  "cognitive":{"modes":["direct"],"forcing_triggers":[]},
  "social_positions_by_role":{"role-taker":"peer"},
  "group":{"group_facing":false,"independence_required":false,"source_disclosure_required":false,"consensus_requirements":[]},
  "agreement_disagreement":{"modes":["none"],"required_triggers":[]}
}
```

The object is closed. Normal decision-control resolution first computes the intersection of every active role's `decision_control.allowed` values and the domain tier's `decision_control_levels`. It uses the primary role default when that value is in the intersection; otherwise it uses the lowest-rank value in the intersection. This is the normal resolved decision control. Final authority may replace it only by the exact override rule below. The other six dimensions resolve by intersecting knowledge modes and OR-ing its booleans; retaining primary verification orientation and unioning obligations; unioning cognitive modes and requiring an evaluated forcing trigger for every non-default mode; preserving one social value per role; OR-ing group booleans and unioning requirements; and unioning agreement modes and triggers. Empty intersections reject.

`ActionRef` is exactly `{role_slug: RoleSlug, action_id: Id}`. It resolves only when `role_slug` is active and `action_id` is declared by that active role's catalog `authority.actions`. `role_scoped_authority` is exactly `{RoleSlug: {actions: [ActionRef], prohibited_action_ids: [Id]}}`, with one entry for every active role and no others; each entry's refs have its key as `role_slug`. Candidate agents never emit this field. During deterministic enrichment, code reads the selected primary role followed by selected secondary roles, copies each catalog action record into the corresponding active-role authority entry as an `ActionRef`, copies that role's prohibited IDs, and persists the resulting map in `PlannedAgent` before validating final authority. No model value can add, remove, or select this map. An action is available only when all four conditions hold: its derived ref belongs to active role authority, its action scope is `internal`, the holder's effective resolved control rank is at least its `min_decision_control`, and domain policy permits that effective resolved control. The pipeline rejects external action refs and never authorizes external effects.

`domain_policy.json` is a closed object with exactly the following content:

```json
{"schema_version":"1.0-proposed","decision_control_rank":{"human":0,"shared":1,"agent":2},"impact_tiers":{"unknown":{"decision_control_levels":["human"],"default_decision_control":"human","terminal_gate_modes":["approval"],"default_terminal_gate_mode":"approval","within_system_final_decision":false},"high":{"decision_control_levels":["human"],"default_decision_control":"human","terminal_gate_modes":["approval"],"default_terminal_gate_mode":"approval","within_system_final_decision":false},"medium":{"decision_control_levels":["human","shared"],"default_decision_control":"human","terminal_gate_modes":["approval","review"],"default_terminal_gate_mode":"approval","within_system_final_decision":true},"low":{"decision_control_levels":["human","shared","agent"],"default_decision_control":"agent","terminal_gate_modes":["approval","review","notification"],"default_terminal_gate_mode":"notification","within_system_final_decision":true}}}
```

The parser requires exactly these tiers, ranks, ordering, and values. `DomainAssessment` is exactly `{tier: unknown|high|medium|low, evidence: [Text]}`. The model assesses only tier and evidence; it cannot emit domain permissions.

`final_authority` is singular and mandatory in both candidate and final plans. It is the only final-decision claim location. Initially only `judge` is final-decision-eligible; that statement is mechanically governed by the normative ledger, so a future ledger change changes eligibility only through catalog validation.

Partial example:

```json
{"agent_id":"judge-agent","action_refs":[{"role_slug":"judge","action_id":"issue-final-system-decision"}],"domain_scope":"medium-impact internal decision","decision_control":"shared","terminal_gate_id":"final-gate","rationale":"medium tier permits a within-system final decision with shared control"}
```

Its closed type is `{agent_id: Id|null, action_refs: [ActionRef], domain_scope: Text, decision_control: DecisionControl, terminal_gate_id: Id, rationale: Text}`. `decision_control` is the one selected effective control, not a second advisory control. If `agent_id` is non-null, it resolves to one holder agent; every unique ActionRef is owned by that agent's derived `role_scoped_authority`; each referenced role is final-decision eligible; the tier permits within-system final decision; and the gate is a reachable, policy-valid terminal gate. The selected value is legal only when it is in the domain tier's `decision_control_levels`, in every active role's `decision_control.allowed` set for the holder, and at least every referenced action's `min_decision_control`. When legal, it replaces the holder's normal resolved decision control for every listed ActionRef and MUST be persisted identically as that `PlannedAgent.resolved_design_settings.decision_control`; action availability is then evaluated with that same persisted effective value. No other agent's setting is changed. Otherwise reject; there is no fallback, coercion, or second control. Thus a judge holder with non-null final authority resolves to `shared` at medium and may resolve to `shared` or `agent` at low only when every active role and the low-tier policy allow the selected value. Unknown and high always require null authority and approval gates. Medium permits non-null authority with `shared` control when all other rules pass. If `agent_id` is null, `action_refs` is `[]`, `decision_control` is `human`, no agent setting is elevated, normal defaults remain in force, and every terminal gate is `approval`. At most one holder exists because this is one singular object. Any additional final-authority claim in role data, agent data, graph metadata, or prose-derived field is invalid; there is no tie-breaker.

## 6. Graph, source identity, phases, triggers, and dissent

`InteractionGraph` is a closed object:

```json
{
  "nodes": ["AgentNode or HumanGateNode"],
  "edges": ["Edge"],
  "independent_opinion_boundaries": ["IndependenceBoundary"],
  "aggregation": ["Aggregation"],

```

`TypedInputRef` is exactly one of `{kind:"context",key:Id}`, `{kind:"node_output",node_id:Id,output:Text}`, or `{kind:"external_source",source_id:Id}`. Context keys, output declarations, and sources must resolve. This union is used without alteration by both agent `visible_inputs` and gate `required_inputs`.

`SourceIdentity` is used only on context, provenance, and other input-source records. It is exactly one of:

```json
{"kind":"agent","id":"agent-id","disclosure":"agent-generated input"}
{"kind":"external_system","id":"source-id","disclosure":"external source disclosed"}
{"kind":"human","id":"human-id","disclosure":null}
{"kind":"synthetic_perspective","id":"synthetic-id"}
```

Agent IDs resolve to both a planned agent and its one agent node. External IDs resolve to `ProvenancePolicy.sources`. Human IDs resolve only to `HumanSourceRegistry.sources`. Synthetic IDs resolve only to `synthetic_perspective_registry.entries`; their disclosure is the registry entry's non-empty disclosure, which must contain `synthetic` and state that it does not represent a stakeholder. Synthetic IDs and normalized labels cannot collide with any human-source or stakeholder ID or normalized label. A synthetic SourceIdentity carries no label or disclosure and therefore cannot introduce unverifiable free identity data. Synthetic identity is never a human identity.

The canonical DAG relation is the union of: explicit `Edge.from -> Edge.to`; producer agent node to an agent/gate that names its output in a typed input; producer agent node to an aggregator that names its output; and aggregator node to its destination gate when the gate requires the aggregation output. This is the only relation used for reachability, entry/terminal checks, phase checks, taint checks, aggregation delivery, and disagreement delivery. It must be acyclic. Every relation from one graph node to another moves to a strictly greater `phase`; thus every explicit edge also moves to a greater phase. Every node is reachable from an entry agent node, every path terminates at a human gate, and at least one terminal gate exists.

Every role-accumulated required trigger must have exactly one `TriggerEvaluation`; no unrelated trigger ID may be present. Its evidence refs resolve to the appropriate registry, assessment evidence index, or declared output. Semantic truth of `result` and rationale remains model-assessed; the validator enforces only structural completeness and resolution. When a required trigger evaluates true, its required disagreement role/path must exist: `second-opinion` for `high-impact`, `uncertainty`, or `user-requested-challenge` when that role requires it; `alternative-perspectives` for `convergence-risk`; `counterargument` for `user-requested-challenge`; `minority-opinion` for `majority-opinion` or `consensus-formation`; and `knowledge-checker` for `conflicting-evidence` or `external-model-output-present` where active role policy requires it. The output of each required role must reach a terminal gate through the canonical relation.

Every active role with `independence_required` appears in at least one boundary. For each boundary, an isolated agent cannot receive a blocked output directly or transitively through any canonical relation, typed input, or aggregation while its phase is less than `release_phase`. Aggregators cannot relay blocked output before release. This is a transitive taint check, not a direct-input check.

An aggregation's aggregator is an agent node; every input is a typed node-output ref; its output is declared by that node; its destination is a reachable terminal gate; and that gate's `required_inputs` contains the same typed node-output reference. A consensus-generator requires reachable alternative-perspectives or counterargument input, reachable minority-opinion input, and an aggregation with `preserve_unresolved_disagreement: true`. A minority output reaches a terminal gate whether adopted or not.

If `unresolved_disagreement.triggered` is true, reason, gate, and output are non-null; output resolves and reaches that terminal gate; the gate requires the output; and an aggregation preserving disagreement exists. If false, all three nullable fields are null. A triggered disagreement must correspond to at least one true required disagreement trigger.

Gate policy is exact: unknown and high permit only approval; medium permits approval or review; low permits approval, review, or notification. If final authority is null, every terminal gate is approval. `approval` remains proposed until explicit approval; `review` is bounded synthesis requiring review; `notification` is bounded low-impact synthesis. No gate mode authorizes an external effect.
